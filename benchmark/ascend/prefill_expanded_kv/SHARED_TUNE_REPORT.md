# 共享专家多流劣化定位与双特性优化验收

已达到目标：双特性同时开启，在实际完成 **9.863 QPS** 时，平均 E2E **1.334 s**。物理卡 6 为 P、7 为 D；两档各 500 请求 × 2 次，共 2000 条正式请求全部成功。

代码分支为 `opt/p_kv_shared_tune`。正式压测的应用代码提交为 `7027a44515bf1a00417e8c5921f2b3d9eac531cf`；后续提交仅补齐复现脚本、说明和本报告，不改变推理代码。

## 根因结论

共享专家多流存在真实设备重叠，也存在算力竞争，但这次服务性能大幅劣化的主要原因是：**展开 KV 占用静态显存后，多流执行的临时工作集缺少余量，触发分配器重试，主机下发停顿被请求排队放大。**

真实模型 profiling 中，取相同 24,721-token 批次，丢弃前两次采集后，对余下三次采集的 138 个层实例统计中位数：

| 执行方式 | MoE 窗口 | Routed GMM2 | Finalize | Shared down |
| --- | ---: | ---: | ---: | ---: |
| 串行 | 5.132 ms | 0.774 ms | 0.276 ms | 0.190 ms |
| 原始 staged 多流 | 4.653 ms | 0.852 ms | 0.328 ms | 0.256 ms |

gate/up 和 down 的重叠比例中位数均为 100%。虽然 GMM2、Finalize 等变慢，MoE 总窗口仍缩短约 9.3%，因此单纯的算力竞争不足以解释数秒级 E2E 劣化。

无 profiler 的真实模型对照进一步定位到显存预算。以下各为原始数据集 500 条请求、名义 9.7 req/s、相同展开 KV 与 allocator 配置，使用 forward 前后分配器计数探针：

| 配置 | 实际 QPS | 平均 E2E | 正式请求期间 forward 内分配重试 |
| --- | ---: | ---: | ---: |
| 多流关闭，P mem fraction .90 | 9.572 | 1328.5 ms | 0 |
| 原始多流开启，P mem fraction .90 | 8.474 | 5423.9 ms | 41 |
| 保留原始多流，仅 P mem fraction 改为 .85 | 9.575 | 1162.9 ms | 0 |

大于 20K token 的 host forward 中位耗时从约 94 ms 增长到 1078 ms；41 次重试全部发生在正式请求的 forward 内。降低 KV 静态预算、保留原始辅助流即可消除重试并恢复性能。这支持临时显存余量不足的因果判断；尚未把额外工作集精确归属到某一个张量。

尝试过仅重叠 gate/up 的调度：独立算子正确，但整网服务性能不达标，已从最终执行路径移除。强制主流实验未取得足够可靠的流身份证据，未用作结论依据。诊断探针也已移除。

## 落地优化

新增 P 端容量参数 `SGLANG_NPU_PREFILL_TRANSIENT_RESERVE_MB`，在 paged KV 容量计算前预留实测所需的临时显存，默认 0 保持原行为。本轮取 **5120 MiB**，P/D 的 `mem_fraction_static` 仍为 .90。

该参数预留的是容量，不额外申请占位张量。保留页对齐和 dummy page 的计费；拒绝负值、非 NPU PD prefill 使用，以及不足一页的预算。显式 token 上限仍按绝对 token 数处理。

代价是 P 端 KV 容量从未预留时约 54,144 降至 **48,896 token**。单次 prefill 的新 token 上限保持 **32,768**，实际压测包含多请求批次。展开 K/V 的布局、精度和 latent PD 传输不变，D 端仍用 latent 缓存。本轮 5 GiB 是当前模型、硬件和负载下的实测选择，不是通用常数。

## 最终独立双特性验收

P：展开 KV=1、多流=1、MIN_TOKENS=8192、RESERVE_MB=5120、ANNOTATE=0。D：展开 KV=0、多流=0。两端均 `expandable_segments:True`、TP1、max-running=64，显式拆分共享专家。正式计时无 profiler、无内存诊断探针。

数据集 `/mnt/sfs_turbo/hxd/CHAT-mxfp8-customer-2000.jsonl`，SHA256 `bb722901ab4a6857571837bbef58b30a4ca00ce08c1aaf170ada3c94694d0f0a`。参考 `bench_glm.sh` 的 rate 压测，固定 seed=42、thinking=true、客户端 max-concurrency=500。每次新服务先准备 100 条；每次正式测试按客户端流程预热后成功 flush cache。此处为 rate 验收，区别于此前固定并发 8、100 条的探索测试。

| 名义 rate | 重复 | 实际完成 QPS | 平均 E2E ms |
| --- | --- | ---: | ---: |
| 9.7 | 1 | 9.5613 | 1159.60 |
| 9.7 | 2 | 9.5646 | 1173.11 |
| **9.7** | **合计** | **9.5629** | **1166.35** |
| 10.0 | 1 | 9.8625 | 1317.90 |
| 10.0 | 2 | 9.8631 | 1349.62 |
| **10.0** | **合计** | **9.8628** | **1333.76** |

实际 QPS 按完成请求数 / 总测量时长计算，包含请求节奏与收尾；合计为 1000 / 两次 duration 之和。每次 500 条输入/输出长度数组完全一致，总输入 1,951,677 token、总输出 14,497 token。错误数均为 0。每次的调度日志审计确认 `max_new_tokens <= 32768`，实际达到 32768。

历史相同名义 10 req/s 对照中，展开 KV 单特性为 9.858 QPS / 1580.4 ms，未预留余量的双特性为 9.068 QPS / 3895.7 ms。本轮预留后的双特性为 9.863 QPS / 1333.8 ms。相对历史双特性实际吞吐约提高 8.8%。这些是顺序实验，未宣称随机交错实验的统计显著性，也未证明更高 rate 或长时间稳态下的容量极限。
